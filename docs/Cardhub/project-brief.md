# 项目简报：Cardhub

#### **执行摘要**

Cardhub 旨在成为一个“维基百科”式的权威卡牌知识分享与社区交流平台，致力于解决目前（尤其在中国市场）缺少专业、集中的卡牌信息来源的痛点。本应用初期将通过一个简洁的 Web 应用，为新手用户提供易于访问的卡牌数据库和系列介绍，并通过用户评论功能促进社区交流，以此建立核心价值。长期来看，Cardhub 计划扩展到所有主流平台，并逐步集成交易、智能估价及专业评级等服务，以满足核心玩家与收藏家的深度需求。

#### **问题陈述**

当前，实体卡牌市场（尤其是中文环境内）面临着一个核心的**信息鸿沟**问题。对于**新手玩家**而言，了解和识别具体卡牌、理解系列背景和价值是一大痛点，高昂的学习门槛阻碍了他们融入这个爱好。与此同时，**核心玩家与收藏家**也缺乏一个专业、集中且值得信赖的平台来进行深度信息查询和社区交流。

现有解决方案存在明显不足：

- **信息分散：** 卡牌知识散落在各种论坛、社交媒体和非专业的网站上，信息零碎、质量参差不齐且难以检索。
- **缺乏权威性：** 缺少一个像“维基百科”一样，能够提供准确、标准化数据的权威来源，导致信息混乱。
- **本地化不足：** 国外优秀的卡牌网站在国内访问体验不佳，且内容未针对本地市场进行优化，存在语言和文化障碍。

因此，Cardhub 旨在解决这一核心问题，通过打造一个权威、易用、集中的知识分享平台，降低新用户入门门槛，并为资深玩家提供一个可靠的交流与参考工具。

#### **提议的解决方案**

我们将构建一个以“**权威知识库**”为核心的卡牌应用——Cardhub。其核心方法是采用类似“维基百科”的模式，提供一个结构化、易于检索的中央数据平台，用以解决当前市场信息分散和不专业的痛点。

**核心差异化优势:**

- **权威性与中心化：** 与传统论坛不同，Cardhub 将致力于成为卡牌信息的单一可信来源，提供经过整理的、准确的数据。
- **社区驱动的价值验证：** 虽然核心内容由平台维护以保证权威性，但允许用户在每个卡牌页面下进行评论和交流。这种模式既保证了信息的准确性，又利用社区的智慧丰富了内容的深度和时效性。
- **专注的 MVP 启动策略：** 我们将首先推出一个轻量级的 Web 应用，专注于“系列介绍”和“卡牌数据库”这两个最高价值的功能。这将使我们能够快速验证核心理念，并围绕最忠实的用户群体建立初步社区，为后续扩展奠定坚实基础。

**长期愿景：**
Cardhub 的最终目标是发展成为一个覆盖全平台、服务卡牌爱好者整个生命周期的一站式生态系统——从初识、学习，到交流、分享，最终到交易和收藏。

#### **目标用户**

我们将用户分为两个核心群体，但在项目初期（MVP阶段），我们的主要精力将集中在“新手入门者”上。

##### **主要用户群体：新手入门者 (Primary User Segment)**

- **用户画像：** 对实体卡牌感兴趣或刚开始接触的个人。他们可能不具备深厚的专业知识，但有强烈的好奇心和学习意愿。
- **当前行为：** 他们通常通过零散的社交媒体帖子、视频或非专业论坛获取信息，时常感到困惑且难以辨别信息的真伪。
- **痛点与需求：**
  - **痛点：** 最大的痛点在于“认识卡牌”。面对海量卡牌，他们很难获得一个系统性、权威性的介绍，也无从判断卡牌的价值和稀有度。
  - **需求：** 迫切需要一个集中、可靠且易于理解的“引路人”式平台，帮助他们建立对卡牌世界的认知体系。
- **核心目标：** 快速了解一个卡牌系列或单张卡牌的具体信息，为自己的兴趣或初次购买决策提供信息支持。

##### **次要用户群体：核心玩家与收藏家 (Secondary User Segment)**

- **用户画像：** 拥有丰富经验的卡牌玩家、交易者或收藏家。他们对卡牌有深入的理解，并积极参与社区活动。
- **当前行为：** 频繁使用现有的、通常是国外的数据库和论坛，但对这些工具的本地化体验和社区氛围并不完全满意。
- **痛点与需求：**
  - **痛点：** 缺少一个能将高质量数据库与深度、专业的社区讨论无缝结合的平台。
  - **需求：** 需要一个分享专业见解、进行高质量交流的“大本营”，并希望这些交流能与一个权威的数据库直接关联。
- **核心目标：** 在一个专业的环境中进行讨论和分享，验证信息，并与其他同好建立联系。

#### **目标与成功指标**

- **商业目标:**
  - **核心目标:** 6个月内达到 **5,000 月活跃用户（MAU）**，验证产品模式。
  - **挑战目标:** 6个月内达到 **10,000 月活跃用户（MAU）**，实现市场渗透。
  - **社区启动:** 3个月内，用户生成有效评论超过 5,000 条。
  - **用户留存:** 实现 20% 的次月留存率。
- **用户成功指标:**
  - **信息获取效率:** 用户能在3次点击内找到目标信息。
  - **内容满意度:** 用户在知识页面上的平均停留时间超过90秒。
- **关键绩效指标 (KPIs):**
  - 月活跃用户数 (MAU)
  - 新用户注册数
  - 次月留存率
  - 日均评论总数

#### **MVP 范围**

我们的 MVP (Minimum Viable Product - 最小可行产品) 旨在用最小的成本，快速验证 Cardhub 的核心价值主张。

##### **核心功能 (Must Have)**

- **卡牌数据库:** 一个结构化的数据库，包含卡牌的详细信息、图片、所属系列等。
- **系列介绍:** 提供各个卡牌系列的背景、历史和清单的介绍页面。
- **卡牌页评论与交流:** 用户可以在每个独立的卡牌或系列介绍页面下发表评论和进行讨论（需登录）。
- **平台:** 功能将通过一个对移动端友好的 **Web 应用程序** 提供。

##### **MVP 范围之外的功能 (Out of Scope)**

- 独立的社区论坛模块
- 用户间的卡牌交易系统
- 手机扫描估价
- AR（增强现实）鉴卡
- 官方担保交易服务
- 专业的卡牌评级提交服务
- 原生 App（iOS/安卓）和桌面端应用

##### **MVP 成功标准**

MVP 的成功将通过我们设定的“核心目标”来衡量：达到 5,000 MAU，用户参与度指标强劲增长，并实现 20% 的次月留存率。

#### **发布 MVP 后的愿景**

##### **Phase 2 功能**

- **独立社区论坛：** 推出一个功能完整的独立论坛模块。
- **交易信息板：** 上线“交易信息板”功能，允许用户发布交易意向，但具体沟通和交易在站外完成。
- **小程序支持：** 推出核心功能的小程序版本，以利用社交平台的传播优势。

##### **长期愿景与扩展机会**

- **一站式生态系统：** 发展为覆盖全平台、服务卡牌爱好者整个生命周期的一站式生态系统。
- **智能化工具集成:** 引入扫描估价、AR 鉴卡等创新工具。
- **全平台覆盖:** 开发原生 iOS/安卓 App、以及 Windows/macOS 桌面端应用。

#### **技术考量**

##### **平台需求**

- **MVP 阶段：** **Web 浏览器** (采用响应式设计)。
- **Phase 2 阶段：** **小程序** (以微信为首)。
- **长期愿景：** **iOS App, 安卓 App, Windows 桌面端, macOS 桌面端** (Tauri 框架)。

##### **技术偏好**

- **后端技术栈：** Rust, PostgreSQL, Redis
- **前端技术栈：** React, TypeScript, Vite, shadcn/ui, TailwindCSS, Zustand, SWR, PNPM, Turborepo
- **客户端存储：** Web 端使用 IndexedDB + localStorage；Tauri 客户端使用 SQLite。

##### **架构考量**

- **代码仓库结构：** **Monorepo**，托管于 GitHub 私有仓库。
- **服务架构：** MVP 阶段采用**单体服务 (Monolith)**。

#### **限制与假设**

##### **限制 (Constraints)**

- **资源限制：** 个人项目，开发资源主要为您的时间和精力。
- **技术学习曲线：** 后端技术栈选用了您正在学习的 Rust，初期开发速度可能受影响。

##### **核心假设 (Key Assumptions)**

- **市场假设：** 一个集中的、高质量的卡牌知识库能有效吸引并留住目标用户。
- **社区假设：** “登录后评论”的功能足以在早期形成社区氛围。
- **技术可行性假设：** Rust 及其生态系统能够满足项目从 MVP 到长期愿景的所有功能需求。

#### **风险与开放问题**

##### **主要风险 (Key Risks)**

- **执行风险：** Rust 的学习曲线可能延迟 MVP 的发布时间。
- **范围蔓延风险：** 过早投入长期愿景功能的开发，影响核心 MVP 交付。
- **竞争风险：** 在开发期间可能会有类似定位的竞争者出现。

##### **开放问题 (Open Questions)**

- 前端状态管理库尚未在 Zustand 和 MobX 之间最终确定。
- 核心实体的详细数据模型和数据库表结构需要进一步设计。
- 项目的长期商业模式和盈利方式尚未定义。
